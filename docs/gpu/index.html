Getting Started with GPU

Miri is GPU-first: running code on an accelerator is part of the language, not a library bolted on top. A GPU program in Miri reads top-to-bottom as a sequence of plain operations, and the cost of each line — upload, kernel launch, readback — is visible in the source.

This guide is built around the residency surface: the small set of keywords that move data onto the device and launch work over it. Everything in the Cookbook compiles and runs today; the snippets are the same ones the compiler verifies in its test suite (cargo test docs::gpu).

Requirements. You need a Miri build (make build, see the install guide) and a GPU adapter reachable through WebGPU — any modern Metal, Vulkan, or DirectX 12 device. If no adapter is present the program reports the GPU as unavailable rather than crashing.

Introduction: residency is a binding attribute

Miri does not have a separate "GPU array" type. An Array<f32, 4> is the same type whether it lives on the host or the device — what differs is the binding's residency. Residency is an attribute on the binding, exactly like mutability:

let  x = [1.0, 2.0, 3.0, 4.0]      // host-resident, immutable
var  y = [1.0, 2.0, 3.0, 4.0]      // host-resident, mutable
gpu let a = [1.0, 2.0, 3.0, 4.0]   // device-resident, immutable  (uploaded)
gpu var d = [0.0, 0.0, 0.0, 0.0]   // device-resident, mutable

Two axes — mutability (let/var) and residency (host/gpu) — give four binding forms and zero new types. The gpu keyword is the only source of device residency. Reading any file, grep 'gpu let\|gpu var' enumerates every device-resident binding.

The residency surface

Four keywords cover the whole surface:

FormMeaningCost
gpu let g = …Immutable device bufferUpload (deferred to first capture)
gpu var g = …Mutable device bufferUpload (deferred to first capture)
gpu forall i in 0..nLaunch a kernel over indices 0..nKernel launch
let h = gCopy a device buffer back to the hostFence + readback

A gpu forall body is a kernel: one GPU thread runs per index. It may capture device-resident bindings, index into them, and do arithmetic, if, and while. It may not do I/O, allocate, or capture host scalars — coefficients live as literals in the kernel body.

What may be device-resident

A type can be bound with gpu only if it implements the Accelerable capability trait. The standard library ships impls for Array<T, N> and List<T> over the accelerable scalars — int, i32, i64, u32, u64, f32, f64, bool — plus tuples and structs whose every field is accelerable. String, Map, Set, and function values are not accelerable; binding one with gpu is a compile error that names the missing trait.

No silent promotion. A host Array never becomes device-resident because a kernel wants it. You write gpu let at the binding, and the upload is visible at that line.

Cross-residency readback — the only way back

Assigning a device-resident binding to a host binding copies the bytes back to the host. This is the only way to read device results, and it is always visible at the assignment line:

gpu var d = [0.0, 0.0, 0.0, 0.0]
gpu forall i in 0..4
    d[i] = d[i] + 1.0

let host = d        // fence + readback — the whole buffer comes back here
println(f'{host[0]}')

There is no .to_host() method and no hidden transfer. One concept, one surface: the keyword on each side of the assignment marks the host/device boundary. The reverse direction works the same way — gpu let g = host_x uploads host_x.

The four cost classes

Every operation is one of four cost classes, and the surface form names the class. You can read the cost of a program straight from the source, without running it:

Cost classSurface marker
Pure host oplet, var, for, a call to a non-gpu function
Upload to devicegpu let, gpu var (paid lazily at first capture)
Kernel launchgpu forall, a gpu fn call
Fence + readbackCross-residency assignment (let h = g)

The runtime exposes counters so you can confirm the cost class of each line. After gpu_reset_telemetry(), the functions gpu_uploads(), gpu_launches(), gpu_readbacks(), and gpu_fences() return the cumulative counts. The buffer-reuse recipe below asserts them directly.

The forbidden pattern — element cross-read

Reading a single element of a device-resident binding from host code is a compile error. It looks harmless, but each read would force its own readback — in a loop, that is N round-trips instead of one bulk copy:

gpu var arr = [0, 0, 0, 0, 0, 0, 0, 0]
gpu forall i in 0..8
    arr[i] = i * i

let v = arr[0]     // COMPILE ERROR: a per-element read would require a readback

The fix the compiler points to is to bulk-copy first, then index the host copy. This keeps the readback cost visible at one line:

Parallel reduction

Planned — not yet runnable. On-device parallel reduction (.reduce lowering to a tree reduction over workgroup memory, returning a scalar) is tracked as F13. The snippet below shows the intended surface. Until F13 ships, sum on the host after a readback.

use system.gpu

gpu let data = [1, 2, 3, 4, 5, 6, 7, 8]
let sum = data.reduce(0, fn(a int, b int) int: a + b)   // launch + scalar fence
println(f'sum = {sum}')                                  // 36

The reduce result is a host scalar, so the fence is implicit but bounded — a single 4-byte readback.

API reference

The residency surface (gpu let / gpu var / gpu forall / readback) runs today. The kernel-authoring surface below — gpu fn, the kernel context, atomics — is the designed API; parts still landing are marked Planned (F…) and excluded from the verified snippet set.

Accelerable

The capability trait that gates device residency. The compiler dispatches on the trait, never on a type name, so adding a new GPU-eligible container is an .mi edit, not a compiler change.

public trait Accelerable
    fn byte_size() int
    fn binding_kind() AcceleratorBindingKind   // Storage | Uniform | PushConstant

gpu let / gpu var

Declare a device-resident binding. gpu let is immutable, gpu var is mutable. The initializer is an array literal or a sized constructor (Array<f32, N>()). Upload is deferred to the first kernel that captures the binding.

gpu forall

Launch a kernel over an index range. The bound may be an integer literal, a const, or a runtime value (0..n, 0..g.length()). The body runs once per index on its own thread and may capture device-resident bindings, index them, and use arithmetic, if, and while. A two-dimensional form gpu forall x, y in 0..W, 0..H is available for literal bounds.

gpu fn and the kernel context

A named kernel. Every parameter is implicitly device-resident, and the body has an implicit kernel context object exposing the launch geometry:

gpu fn scale(src Array<f32, 1024>, dst out Array<f32, 1024>)
    let i = kernel.thread_idx.x + kernel.block_idx.x * kernel.block_dim.x
    if i < src.length()
        dst[i] = src[i] * 2.0

The four launch-geometry fields below are available today, each with .x, .y, and .z components:

FieldMeaningStatus
kernel.thread_idxThread index within its blockAvailable
kernel.block_idxBlock index within the gridAvailable
kernel.block_dimThreads per blockAvailable
kernel.grid_dimBlocks per gridAvailable
kernel.global_idxblock_idx * block_dim + thread_idxPlanned (Task 3 follow-up)
kernel.barrier()Workgroup synchronizationPlanned (F32 / F36)
kernel.warp.*Subgroup / warp ops (lane_id, shuffle_down, …)Planned (F17)

Planned. A gpu fn can be defined today, but the explicit .launch(grid = …, block = …) dispatch surface is still landing. For runnable kernels today, use gpu forall, which infers the launch geometry for you.

Atomics

Planned — F11 / F18. Atomic<T> for T ∈ {i32, u32} with load / store / add / sub / max / min / and / or / xor / compare_exchange is the escape hatch for concurrent writes that aren't a 1-to-1 function of the thread index. Until it ships, kernels must write each element from exactly one thread.

system.math on the device

The system.math intrinsics are usable inside kernels: abs, min, max, pow, sqrt, floor, ceil, round, sin, cos, tan, log, exp.

Known limitation (F23). A math intrinsic whose result is consumed by an f32 buffer is being narrowed to the buffer width; mixed-width math in kernels can produce wrong values on some adapters until F23 is fully verified. Prefer host-side math for now where precision matters.

WGSL backend limits

Miri's first GPU backend targets WebGPU (WGSL) through wgpu, the most portable Rust GPU host driver. WGSL's core lacks several features, so the following are gated until the native backends (SPIR-V, PTX, Metal) land. Each gap names the follow-up that closes it:

Not in WGSL coreConsequenceClosed by
Native i64 / u64 / f6464-bit scalars are gated on device features; an unsupported adapter is refused before dispatch (not at runtime)Native backends (M8)
64-bit atomicsAtomic<i64> / Atomic<u64> unavailable on WGSLF11 / F18 + native backends
Cooperative matrixNo tensor-core / cooperative-matrix pathNative backends (M8)
fp8 / fp4 / bf16Low-precision types cannot lower to WGSLF9 (and follow-ups) + native backends
f16No half-precision primitive type yetF9

WGSL stays the browser and embedded path. The native primaries — SPIR-V, PTX, Metal — target these features directly once the surface stabilizes. WGSL-first is an implementation milestone, not a long-term ranking.

Review checklist — verifying GPU code

A reviewer (human or LLM) verifying a Miri GPU change should answer these six questions in order. If any answer is "no" or "not visible", the change needs work.

  1. Residency. Does every GPU-touching binding start with gpu let / gpu var? Does every gpu forall capture refer to a device-resident binding? Does every gpu fn parameter type implement Accelerable?
  2. Cost classes in order. List the cost events (upload, launch, fence + readback). Does the order match the source top-to-bottom? Are there any unexpected fences beyond a cross-residency assignment?
  3. Buffer reuse. Do adjacent gpu forall blocks over the same gpu var share the buffer (no cross-residency assignment between them)? Is there any let h = g; …; some_kernel(g) where the readback is wasted?
  4. Mutability. Is every captured gpu var element written by exactly one thread? Concurrent writes to a non-Atomic element are a compile error. For shared-memory patterns, is every shared write followed by a kernel.barrier() before another thread reads it?
  5. Bounds + indexing. Does every in-kernel arr[i] have a visible bounds guard when the index isn't bounded by the iteration range? In host code, are all indices into device-resident bindings forbidden (caught by the compiler) or bulk-copied first?
  6. Portability. Does the change rely on any backend-specific path or hardware feature? If so, is each one necessary, and is the requirement stated near the kernel?

What's Next

You can now write, compile, and run GPU programs using the residency surface: declare device buffers with gpu let / gpu var, launch kernels with gpu forall, and read results back with a cross-residency assignment.

Coming next on the GPU roadmap:

  • On-device reduction — .reduce over workgroup memory returning a device scalar (F13).
  • Shared memory + barriers — var<workgroup> tiling and kernel.barrier() (F32 / F36).
  • Atomics — Atomic<i32> / Atomic<u32> for scatter and histogram patterns (F11 / F18).
  • Warp / subgroup ops and low-precision types (f16, bf16, fp8) — F17, F9.
  • Native backends — SPIR-V, PTX, and Metal for the features WGSL core can't express (M8).

Found a rough edge? The GPU surface is evolving fast — open an issue on GitHub.
